## 讲了什么／实际看到了什么

**AI SDK UI 是前端状态层，不是组件库。** 文档自述它是 framework-agnostic 工具包，核心是三个 hook：`useChat`（流式消息 + loading/error 状态，输入状态留给调用方自己管）、`useCompletion`（文本补全）、`useObject`（消费流式 JSON）。支持矩阵列 React / Vue / Svelte / Angular / SolidJS（社区），外加一列 MCP Apps（只 React 有）。整份 `ai-sdk-ui` 文档共 14 页，没有一页是组件。

**真正值得看的是它的消息类型协议。** `UIMessage.parts` 是一个带判别式的数组，part 类型包括 `text`、`reasoning`、`source-url`、`source-document`、`file`、`data-*`（自定义数据）、`tool-${toolName}`（按工具名生成的具名类型）、`dynamic-tool`、`step-start`、`custom`、`steering-message`（实验性）——共 11 种。工具 part 自带状态机，文档里出现的取值是 `input-streaming` → `input-available` →（可选 `approval-requested` → `approval-responded`）→ `output-available` | `output-error` | `output-denied`。流协议页面逐节定义了 27 种 wire part（起止两段的小节标题是 “Message Start Part” 与 “Finish Message Part”，wire `type` 值其实是 `start` 和 `finish`；27 种为：`start`、text start/delta/end、reasoning start/delta/end、`reasoning-file`、`source-url`、`source-document`、`file`、`custom`、`data-*`、`error`、tool-input start/delta/available、tool-approval request/response、`tool-output-available`、`tool-output-denied`、`steering-message`、`start-step`、`finish-step`、`reset-step`、`finish`、`abort`，外加 `[DONE]` 终止标记——终止标记不计入 27）。

**它所谓的「Generative UI」不含 UI。** `generative-user-interfaces` 整页的做法是：定义 tool（zod inputSchema + execute）→ 在 `message.parts` 里 `if (part.type === 'tool-displayWeather')` → `switch (part.state)` 手写 `input-available` / `output-available` / `output-error` 三个分支 → 渲染自己写的 `<Weather {...part.output} />`。组件由开发者提供，SDK 只负责把 tool 结果送到位。加一个工具就要在页面里再抄一遍整段 switch。

**MCP Apps 是另一条、不经过你的组件库的 UI 通路。** MCP server 的 tool 可以带 `_meta.ui.visibility` 并指向一个 `ui://` 资源（MIME `text/html;profile=mcp-app`）；host 读到后用 `MCPAppRenderer` 把这段 HTML 放进沙箱 iframe，iframe 里的 tool 调用通过 host 代理回 MCP server。文档明确把这段 HTML 当不可信内容，**建议**走独立 origin 的 sandbox 代理路由（原文是 “ideally”，不是硬要求），并硬性要求只把 `modelVisible` 工具给模型、每次 iframe 请求都在服务端校验。

**组件层是另一个产品，而且正在搬家。** `elements.ai-sdk.dev`（AI Elements，49 个组件页，`ai-elements` npm 1.9.1）站顶横幅写着「AI Elements is moving to shadcn/ui. This project will be deprecated at the end of November 2026.」接替的是 shadcn/ui 文档下的 **AI Elements patterns，21 个**：Chain of Thought、Chat、Checkpoint、Confirmation、Context、File Tree、Inline Citation、Message、Model Selector、Plan、Prompt Input、Queue、Reasoning、Sources、Stack Trace、Subagent、Suggestion、Task、Terminal、Test Results、Tool。它的说法是「patterns for agentic interfaces, built from shadcn/ui components」、没有包可装、代码是你的。页内「Migrating from AI SDK Elements」一节（没有独立迁移页）给了一张 26 行的旧文件 → 新目标对照表，其中 5 行的目标是普通 shadcn/ui 组件而不是 AI Elements pattern（Attachment / Questionnaire / Code Block / Trace / shimmer）；并明说另有 16 组、共 23 个旧组件文件（artifact、audio-player、canvas/connection/controls/edge/node/panel/toolbar、environment-variables、image、jsx-preview、mic-selector/voice-selector、open-in-chat、package-info、persona、sandbox、schema-display、snippet、speech-input、transcription、web-preview）**不做替代**，理由是使用量低、都能用已有组件拼出来。

**结构上它做了一件 Oreo 没做的事：抽公共原语。** shadcn 的介绍句是「A Chat is a list of Message turns inside a Message Scroller. The steps an agent takes inside a turn, like Reasoning, Tool and Plan, are built on Trace, so every step has the same shape.」——逐页核验（2026-11-16），21 个 pattern 里有 13 个直接 import `@/components/ui/trace`：Chain of Thought、Chat、Confirmation、Plan、Queue、Reasoning、Sources、Stack Trace、Subagent、Task、Terminal、Test Results、Tool，共享同一个 `Trace` 原语，所以每一步的形状一致；起步命令就是 `shadcn add trace code-block`。

## 实现方式

已核实（文档正文 + npm registry + 本仓库 grep）：

- 三个 hook 与 MCP Apps 的分工、支持矩阵、part 类型与状态机、流协议 part 清单：来自上列文档页与 `llms.txt` 全文语料。
- 版本与许可：npm registry 当日 `latest`。
- AI Elements 弃用：**来自 `elements.ai-sdk.dev` 站顶横幅与 shadcn/ui AI Elements 页内的迁移一节**，未见正式 changelog 或 release note，日期表述只精确到「11 月底」。
- Oreo 侧：`src/components` 144 个目录、`src/patterns` 93 个目录（一个目录常导出多个组件，`test-results` 6 个、`web-search` 8 个，所以 144 是下限不是组件数）；对 `ai-sdk` / `@ai-sdk` / `ai/react` / `useChat` / `UIMessage` / `ToolUIPart` / `streamText` / `ai-elements` 做全仓库 grep（排除 `node_modules`）：`src/` 与 `README.md` **全部零命中**；`docs/` 下只有本记录自身及其 `catalog.json` 条目，以及 2026-11-13 Astryx 记录里 `useChat` 作为 Meta 自有 hook 名（`useChatDictation` 等）的子串命中。所以 Oreo 当前与 AI SDK 没有任何代码关系。
- Oreo 现有 prop 词汇（读源码，以下为**节选**，这些组件都另外继承宿主元素属性）：`ToolCallProps.state?: "running" | "complete" | "error"`（`src/components/tool-call/tool-call.tsx:20`，默认 `"complete"`）；`ReasoningProps.status?: "running" | "finished"`（`src/components/reasoning/reasoning.tsx:14`，默认 `"finished"`）；`MessageProps = { role: "user" | "assistant"; avatar? } & MessageVariants & ComponentPropsWithoutRef<"div">`（`src/components/message/message.tsx:18`——`children` 是从 div 属性继承来的，不是声明的 prop）；`ContextWindowProps` 除 `capacity` / `usage {system,tools,conversation,memory}` / `files` 外还带 `model?` / `onRemoveFile?` / `onCompact?` / `onNewChat?` / `compacting?` / `compactError?` / `defaultFilesOpen?`（`src/components/context-window/context-window.tsx:11-24`，已经不是裸数据形状）；`SourceProps = { domain; title; icon? } & Omit<…"a", "title">`（`src/components/sources/sources.tsx:53`）。
- `src/components` 与 `src/patterns` 下没有任何 `fetch(` / `EventSource` / `WebSocket` / `ReadableStream`；流式效果都是本地模拟（`ReasoningGroup` 的 `stream` / `stepInterval`、`src/docs/playground/web-search.demo.ts` 的定时节拍）。唯一的网络行为是文档站外壳里的 `@vercel/analytics`（`src/main.tsx:3`），不在任何组件里。

## 对 Oreo UI 的启发

**1. 这是 Oreo 缺的那一层，而且不抢 Oreo 的位置。** Oreo 144 个组件目录 / 93 个 pattern 里 agent 界面占了很大比重（message、prompt-box、composer、conversation、response、reasoning、thinking-state、streaming-text、tool-call、sources、web-search、context-window、model-routing、model-usage、subagents、terminal、test-results、plan、agent-runs / agent-inbox / agent-lanes / agent-task-queue / agent-observability、confirmation、inline-confirm、attachment、code-block、code-diff），但全部是 presentational + 本地 fixture。AI SDK UI 正好只做状态与协议、不带组件。两边是互补关系：Oreo 是视图，AI SDK UI 是数据源。

**2. 最值得采用的不是依赖，是类型词汇。** 建议不要给 Oreo 加 `ai` / `@ai-sdk/react` 运行时依赖——理由不是「会破坏 copy 一个文件夹就能用」（仓库本来就有 23 个运行时依赖且组件直接 import：`src/components` 与 `src/patterns` 下 `@base-ui-components/react` 64 个文件、`motion/react` 59 个，全 `src` 为 67 / 78；`tool-call` 和 `reasoning` 自己就靠这两个），而是把设计系统的公开 prop 类型绑到单一厂商的协议包上，会让 Oreo 跟着它的破坏性改版走——`ai` 已经到 7.x，v5→v6 就改过 `isToolUIPart` → `isStaticToolUIPart` 并新增了三个工具状态。（README 里逐组件写的「no new dependencies」`README.md:56,137,151,161,179` 说的是单个组件复制时的依赖面，不是仓库级禁令，不宜当主要论据。）该做的是让组件 props **形状对齐 `UIMessage` part**，取值用 Oreo 自己声明的本地 union 字面量照抄 AI SDK 的字符串，既不 import 也不加 `peerDependencies`——仓库的分发方式是整目录复制，给 `ai` 加 peer 等于让所有复制者装一个大多数用不到的包。证据是现在对不上：Oreo `ToolCall.state` 三态对 AI SDK 的七态，`input-streaming`（参数还在流式生成）、`approval-requested`（等人批准）、`approval-responded`、`output-denied`（人拒绝了）这几种状态 Oreo 现在**表达不出来**；`Message` 用 `children` 而不是 `parts[]`，调用方必须自己拆分支。（反过来 `Reasoning.status = "running"|"finished"` 其实已经和 AI SDK 的 `streaming`/`done` 一一对应，这里没有缺口——初稿曾误称它缺 `aborted`，AI SDK 的 reasoning part 并没有该状态。）不对齐的代价不是「多写一个 adapter」，而是 adapter 会静默丢状态——而 tool approval 恰好是 agent 界面里最需要视觉设计的一屏。

**3. 竞争格局变了，差异化要重新收。** AI Elements 弃用 + 并入 shadcn/ui，意味着「AI 组件」正从独立品类被吸收进通用设计系统，并且是免费、`shadcn add` 一行、分发力远超 Oreo 的那一个。shadcn 的 21 个 pattern 和 Oreo 的组件清单高度同名重叠（本次逐项比对，直接同名或明显同角色的 ≥17 个：Chat≈conversation、Tool≈tool-call、Context≈context-window、Model Selector≈model-routing、Prompt Input≈prompt-box、Queue≈agent-task-queue、Suggestion≈chip/ChipGroup、Chain of Thought≈thinking-state+ReasoningGroup、Task≈task-row/grouped-tasks、File Tree≈`FolderTree`、Stack Trace≈`TestStackTrace`（`src/components/test-results/index.tsx:187`，已进 catalog 与 playground）、Inline Citation≈`WebSearchCitation`（`src/components/web-search/search-citation.tsx:10`，由 `WebSearchAnswer` 把引用嵌进流式正文，`search-answer.tsx:51`），加 message / reasoning / sources / plan / subagents / terminal / test-results / confirmation 同名）；Oreo 真正完全没有对位的只有 **Checkpoint 一个**——`branch-picker` 只做分支翻页，没有 restore 语义。File Tree 有近似物 `FolderTree`（`src/components/knowledge-base/knowledge-base.tsx:76`，递归 `children` + 展开折叠 + `aria-expanded`），差别是它只渲染文件夹、不渲染变更文件叶子；`tree-stepper` 是递归嵌套选择器不是文件树，`writing-folders` / `linked-documents` 是平铺列表。所以「我们有 agent 组件」已经不是差异点。可守的差异化是：动效密度与质量（Motion springs + review-animations 门禁）、token 系统与主题切换、成套可跑的 template（93 个 pattern 覆盖多个领域；shadcn 那边只有一个 chatbot template 加零散 pattern）、以及中文设计语言。

**4. shadcn 的 `Trace` 原语是直接可学的结构改进，但 Oreo 缺的那块比「展开行为」更具体。** 核实后要修正这条论据：Oreo 并非毫无共享——`reasoning` 和 `tool-call` 已经共用同一套脚手架（Base UI `Collapsible` + `ActivityLabel` + `@/lib/motion`），`StatusView`（以 `AgentWorkspaceState` 之名，`src/components/automation/index.tsx:67`）被 `src/components` / `src/patterns` 下 104 个文件 import，`StatusIcon` 也被多处复用；`plan` / `subagents` / `terminal` / `agent-runs` 则**根本没有展开行为**，只有 `test-results` 是手写的那一个异类。真正没有共享的是**状态词汇**：同一个「一步做到哪了」被编码成至少八套互不兼容的 union——`tool-call` `"running"|"complete"|"error"`、`reasoning` `"running"|"finished"`、`plan` `"done"|"active"|"pending"`、`subagents` `"running"|"done"|"error"`、`terminal` `running: boolean + exitCode: number`，外加 `thinking-state` 的 `ThinkingRunStatus`（`src/components/thinking-state/index.tsx:120`）、`task-row` 的 `TaskStatus`（`src/components/task-row/index.tsx:5`）、以及已被 15 个文件复用并已进 catalog 的 `StatusIconState`（`src/components/icon/status-icon.tsx:7`）。最后这个是现成的 owner 候选，要统一枚举应该从它开始，而不是另起一套。只有 `tool-call` 适合直接对齐第 2 条的 AI SDK 取值——`plan` / `terminal` / `task-row` 不是工具调用生命周期，硬套 `input-streaming` / `approval-requested` 会比现在更糟。所以可学的是：先统一 Oreo 自己的一套步骤状态枚举（AI SDK 取值只覆盖工具那一支），再考虑抽步骤原语。命名要避开 `Trace`——Oreo 已有 `trace-query` / `trace-explorer`，是可观测性查询 UI，同名不同物。这是建议，不是现行规则。

**5. MCP Apps 是一条值得评估、但目前没有证据的新出口。** 设计系统理论上可以把一个 pattern 打包成 `ui://` HTML 资源，被任意 MCP host（含不用 React 的）渲染。对 Oreo 的门槛是：要自包含单文件 HTML + 内联 CSS（Oreo 是 React 19 + Tailwind v4 + CSS 变量 + Motion）、要过 CSP、iframe 里拿不到宿主主题。要不要做应先做一个最小实验再谈，不要先写进 roadmap。

**不适用的部分**：`useCompletion` 和 `useObject` 对 Oreo 基本无关（Oreo 不做补全框和流式 JSON 渲染器）；transport / message persistence / resume streams / error handling 属应用层职责，设计系统不该代管。
